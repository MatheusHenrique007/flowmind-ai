# PRD — Release v0.6.0: Scheduling

- **Status**: Approved (stakeholder-approved in chat; this document formalizes it)
- **Date**: 2026-08-12

## What problem does this release solve?

Every Workflow execution today needs a human or an external system to call `POST
/webhooks/:workflowId` — there is no way to make a Workflow run on its own, on a recurring
cadence, without wiring up an external cron caller. Product needs a first-class, recurring
trigger: "run this Workflow every N minutes/hours/day" with nothing external required.

## Who is this for, and what is the use case?

Any workspace owner who wants a Workflow to run automatically on a schedule instead of only in
response to an inbound webhook — e.g. "summarize yesterday's support tickets every morning at
9am UTC" or, for demo/testing purposes, "run this every minute so I can see it fire."

## Scope: a Schedule entity, recurring BullMQ registration, nothing else

```
Schedule (Domain) -> CreateSchedule/ListSchedules/DeleteSchedule (Application)
   -> PrismaScheduleRepository + BullMQScheduleQueue (Infrastructure)
   -> POST/GET/DELETE /schedules (API) -> minimal schedules panel (Web)
```

- A `Schedule` belongs to exactly one `Workflow` and one `Workspace`, carries a cron expression
  (UTC only — see "Explicitly out of scope"), and is persisted in Postgres.
- Creating a Schedule registers a recurring job with BullMQ's Job Scheduler API
  (`upsertJobScheduler`), reusing the exact same `workflow-execution` Queue and Worker that
  webhook-triggered runs already use — no new queue, no new worker, no Engine changes.
- Deleting a Schedule unregisters the job scheduler (`removeJobScheduler`) and removes the
  Postgres row. Deleting a Schedule never cancels a run already enqueued or executing — only
  future occurrences stop (BullMQ's native semantics, not something this release builds).
- A hard limit of 20 Schedules per workspace, enforced in the Application layer, not just the UI.
- Cross-tenant access (reading, listing, or deleting another workspace's Schedule, or creating one
  against another workspace's Workflow) reads as 404, matching the existing Workflow/WorkflowRun
  pattern (ADR-0004) — never a distinct 403 code path.
- A minimal frontend surface: create/list/delete Schedules for the workflow currently open in the
  editor, with a visible "UTC only" disclaimer and each schedule's next run time.

Anything not listed above is out of scope — see "Explicitly out of scope" below.

## Explicitly out of scope

- **Timezones.** Cron expressions are evaluated in UTC only. No timezone field on the Schedule
  entity, the API, or the frontend. Stated explicitly in the frontend UI's disclaimer text and in
  ADR-0006. A future release can add timezone support without changing this release's storage
  shape (BullMQ's Job Scheduler API already accepts an optional `tz`, unused this release).
- **Pausing/resuming a Schedule.** A Schedule exists or it doesn't — no intermediate paused state.
  Deleting and recreating is the only supported way to "pause" this release.
- **Editing a Schedule's cron expression in place.** Delete and recreate. An update endpoint adds
  another code path through the exact consistency strategy this release is deliberately keeping
  minimal (see ADR-0006) for no proven need yet.
- **A saga framework, an intermediate status column, or a background reconciliation job** for
  Postgres/BullMQ consistency. The approved strategy is an ordering-plus-compensation rule, applied
  directly in the two use cases — see ADR-0006's full rationale.
- **A workflow picker in the frontend.** The editor only ever knows about the one Workflow it has
  loaded/saved; there is no workflow list anywhere else in `apps/web` yet. The Schedules panel
  schedules the currently-open Workflow, not an arbitrary one chosen from a dropdown that doesn't
  otherwise exist in this app.
- **Any change to `packages/engine` or the BullMQ Worker.** A Schedule produces exactly the same
  `WorkflowExecutionJobData` shape a webhook enqueue already produces (plus one new optional
  `scheduleId` field the Worker never reads) — the Worker's job handler needs zero behavioral
  change.
- **A second BullMQ Queue.** Schedules register against the exact same `workflow-execution` Queue
  instance webhook enqueues already use.
- **Notifying anyone when a Schedule's registration or unregistration fails.** The API surfaces
  the failure synchronously (502/500) to the caller of that HTTP request; no email/Slack alerting
  is added this release.

## Entities

- **Schedule** (Domain, new): `id: ScheduleId`, `workflowId: WorkflowId`, `workspaceId:
WorkspaceId`, `cronExpression: string`, `createdAt: Date`. Validates the cron expression
  structurally (5 space-separated fields, each within its valid numeric range) in `Schedule.create`,
  hand-rolled — no new Domain dependency.

## APIs

- `POST /schedules` — body `{ workflowId, cronExpression }`. 201 with the created Schedule
  (including `nextRunAt`) on success. 404 if `workflowId` doesn't exist or belongs to another
  workspace. 400 for a structurally invalid cron expression or malformed body. 409 at the
  20-schedule-per-workspace limit. 502 if Postgres persisted the row but BullMQ registration then
  failed (the row is deleted before this is returned — see ADR-0006).
- `GET /schedules` — 200 with the caller's workspace's Schedules: `id`, `workflowId`,
  `workspaceId`, `cronExpression`, `createdAt`, `nextRunAt`.
- `DELETE /schedules/:id` — 204 on success. 404 if the id doesn't exist or belongs to another
  workspace (indistinguishable from nonexistent, per ADR-0004).
- All three require the existing `requireAuth` bearer-token preHandler; workspace is always
  derived from the verified token, never from the request body.

## Execution flow

1. `POST /schedules` validates the cron structurally (Domain), verifies the Workflow exists in the
   caller's workspace (reusing `WorkflowRepository`), persists the Schedule row (Postgres), then
   registers a BullMQ job scheduler with the exact `WorkflowExecutionJobData` shape a webhook
   enqueue would produce plus `scheduleId`.
2. On its cron cadence, BullMQ enqueues a `workflow-execution` job exactly as `BullMQWorkflowQueue`
   would for a webhook — the existing Worker (`start-workflow-worker.ts`, unmodified) drains it and
   calls `ExecuteWorkflow`, exactly as today.
3. `DELETE /schedules/:id` unregisters the job scheduler first, then deletes the Postgres row. Any
   run already enqueued or executing at the moment of deletion completes normally — only future
   occurrences stop.

## Real risks this release proves

1. **Postgres and BullMQ/Redis have no shared transaction** — a Schedule row and its BullMQ
   registration can each independently fail without the other knowing. Proved by
   `CreateSchedule`'s compensation test (queue registration failure triggers a Postgres delete) and
   `DeleteSchedule`'s abort test (queue unregistration failure leaves the Postgres row untouched).
2. **A Schedule must produce a real, automatic WorkflowRun with zero manual intervention and zero
   AI provider keys configured.** Proved by the live smoke test: a `*/1 * * * *` schedule against
   the seeded demo Workflow produces a new `WorkflowRun` via `GET /workflow-runs` within ~90
   seconds, using `MockAIProvider`, with no webhook call made.
3. **Deleting a Schedule must not cancel work already in flight.** Proved by relying on BullMQ's
   documented `removeJobScheduler` semantics (future occurrences only) rather than building
   anything that would defeat it, and by the live smoke test observing no further runs after
   deletion.

## Two-minute demo

1. `pnpm demo` boots the stack with zero AI provider keys.
2. Log in, open the seeded demo Workflow, save it, then in the Schedules panel enter `*/1 * * * *`
   and click "Add schedule" — the UTC disclaimer and the schedule's next-run time are visible
   immediately.
3. Wait about a minute; refresh `GET /workflow-runs` (or the panel) — a new `WorkflowRun` appears
   with `status: SUCCEEDED`, using the Mock AI provider's unmistakably-synthetic output, with no
   webhook call made by the demo operator.
4. Delete the schedule. Wait another minute — no further runs appear.

## Acceptance criteria / Definition of Done

- Domain: `Schedule` entity with structural cron validation and unit tests (valid/invalid crons,
  missing ids), no new Domain dependency.
- Application: `CreateSchedule`/`ListSchedules`/`DeleteSchedule` behind `ScheduleRepository`/
  `ScheduleQueue` ports, implementing the exact ordering in ADR-0006, with fake-based tests
  covering the limit, cross-tenant isolation, and both compensation paths.
- Infrastructure: `PrismaScheduleRepository` (workspace-scoped WHERE clauses, real-Postgres
  integration tests including a cascade-delete proof) and `BullMQScheduleQueue` (real-Redis
  integration tests using BullMQ's Job Scheduler API, sharing the existing Queue instance).
- API: `POST`/`GET`/`DELETE /schedules`, wired through `composition-root.ts`, with route-level
  tests covering happy paths, cross-tenant 404s, the 20-schedule limit, and unauthenticated 401.
- Web: a schedules panel on the currently-open Workflow with a UTC disclaimer, no timezone picker,
  no API-key UI.
- `packages/engine` shows zero diff. The Worker shows zero or near-zero diff (at most the optional
  `scheduleId` field's type addition, unused by the Worker's logic).
- Full quality gate (lint/typecheck/test/build) green, and the live smoke test in "Two-minute demo"
  observed with real run ids/timestamps, not simulated.
