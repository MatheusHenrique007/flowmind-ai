# PRD — Release v0.8.0: Observability / Run History UI

- **Status**: Approved (stakeholder-approved in chat; this document formalizes it)
- **Date**: 2026-08-12

## What problem does this release solve?

Executing a Workflow showed the user nothing. `apps/web/components/flow-editor.tsx`'s
`handleExecute()` only displayed a static string — "Queued — check /workflow-runs for the result
once the Worker processes it." — instructing the user to leave the application and call the raw
API themselves. The backend (`GetWorkflowRun`, `ListWorkflowRuns`, `GET /workflow-runs`,
`GET /workflow-runs/:id`) has existed and worked since v0.2.0, but no frontend page ever consumed
it. Worse, `WorkflowRunView` only ever carried a raw `workflowId` — never a human-readable name —
so even the raw API response couldn't tell two Workflows' runs apart without a manual cross-lookup.

## Who is this for, and what is the use case?

Any workspace owner who has just clicked "Execute" and wants to know, without leaving the
application, whether it worked — and anyone reviewing what happened on a past run.

## Scope: consume existing read paths, plus minimal presentation-layer composition

```
WorkflowRunView gains workflowName (Application port, additive)
   -> GetWorkflowRun / ListWorkflowRuns resolve it via the existing WorkflowRepository
   -> GET /workflows composes ListWorkflows + ListWorkflowRuns for a "lastRun" indicator (API)
   -> Run history panel inside /workflows/[id], snapshot-diff polling after Execute (Web)
```

- `WorkflowRunView` (`packages/application/src/ports/workflow-run-view.ts`) gains one optional
  field: `workflowName?: string`. Additive — no existing consumer reads it, nothing breaks.
- `GetWorkflowRun`/`ListWorkflowRuns` (Application) each gain a `WorkflowRepository` dependency to
  resolve that name — `GetWorkflowRun` with one extra `findById` lookup (O(1), one run = one
  lookup), `ListWorkflowRuns` with one extra `listByWorkspace` call (already existed since v0.7.0)
  batched into an in-memory `id -> name` map, never one lookup per run.
- `GET /workflows`'s route handler composes the already-existing `ListWorkflows` and
  `ListWorkflowRuns` use cases to attach a `lastRun: {status, finishedAt} | null` field per Workflow
  — presentation-layer grouping/sorting, not a new Application use case or port.
- The Web app gets a run-history panel inside `/workflows/[id]` (list of past runs plus a
  detail view per run: status, timestamps, per-step status/output/error) and a snapshot-diff
  polling helper that tracks a just-triggered execution from RUNNING through to a terminal status.
- The "My Workflows" list (`/`) shows a simple last-run indicator (success / failure / no runs yet)
  per Workflow.

Anything not listed above is out of scope — see "Explicitly out of scope" below.

## Explicitly out of scope

- **Retry, backoff, dead-letter handling.** Purely a read/display release — execution reliability
  is untouched and deferred.
- **WebSocket or Server-Sent Events.** Plain, bounded polling only (`setTimeout`-based, no new
  dependency), matching this project's existing dependency-minimalism.
- **Aggregate metrics, advanced filters, export.** The panel shows a plain list and detail view —
  no charts, no date-range filters, no CSV/JSON export.
- **Any change to `POST /webhooks/:workflowId`'s response shape.** It still returns exactly
  `{accepted: true}` — no run id. The frontend never assumes otherwise (see "Real risks" below).
- **Any change to `packages/domain` or `packages/engine`.** Nothing here needed either.
- **A Prisma migration or schema change.** `workflowName` and `lastRun` are both computed from data
  that already exists — no new column, no new table.
- **Workflow versioning, RBAC, new integrations.** Unrelated to this release.

## Entities

No new Domain entities or value objects. `WorkflowRunView` (an Application-layer read projection,
not a Domain entity) gains one optional field.

## APIs

No new endpoints. `GET /workflow-runs`, `GET /workflow-runs/:id`, and `GET /workflows` are reused
as-is at the route level — only the data they return grew richer:

- `GET /workflow-runs` / `GET /workflow-runs/:id` now include `workflowName` per run.
- `GET /workflows` now includes `lastRun: {status, finishedAt} | null` per Workflow.
- `POST /webhooks/:workflowId` is byte-for-byte unchanged.

## Execution flow

1. On Execute, the frontend first snapshots the current run ids for this Workflow (via
   `listWorkflowRuns()`, filtered client-side by `workflowId` — there is no server-side filter
   param), then calls the existing `executeWorkflow(id, payload)` unchanged.
2. It polls `listWorkflowRuns()` every 1–2 seconds looking for a run id **not** in the snapshot —
   this avoids misattributing a Schedule-triggered run (or a second manual click) that happens to
   land at the same moment as "the" tracked execution.
3. Once a new run id is found, polling switches to `getWorkflowRun(runId)` specifically until its
   status reaches `SUCCEEDED`, `FAILED`, or `CANCELLED`, or a bounded timeout elapses — never an
   unbounded loop.
4. The run-history panel inside `/workflows/[id]` renders past runs (status, date/time, duration
   computed client-side from `startedAt`/`finishedAt`, step count) and, per run, a detail view of
   every step's status/output/error.
5. `GET /workflows`'s `lastRun` field drives a simple indicator on the "My Workflows" list.

## Real risks this release proves

1. **A manually-triggered execution can be tracked to completion without the backend ever
   returning a run id**, and without misattributing a concurrently-Schedule-triggered run to the
   user's own click — proved by the snapshot-diff strategy and its test coverage.
2. **Enriching a read projection with cross-aggregate data (Workflow name onto a WorkflowRun view)
   is achievable without N+1 queries or a new port**, by reusing `WorkflowRepository.listByWorkspace`
   (already built for v0.7.0) — proved by the batched in-memory lookup and its tests.

## Two-minute demo

1. Open an existing Workflow, click Execute — the panel shows RUNNING immediately.
2. Within a few seconds it flips to SUCCEEDED (via `MockAIProvider` — no API keys needed) and
   appears in the run history list with a timestamp and duration.
3. Click into that run — see each step (Trigger/AI/Destination) with its status and output.
4. Go back to "My Workflows" — the list shows a success indicator next to this Workflow.

## Acceptance criteria / Definition of Done

- Application: `WorkflowRunView.workflowName` resolved correctly by both `GetWorkflowRun` (single
  lookup) and `ListWorkflowRuns` (batched lookup, no N+1), with tests covering multi-workflow lists
  and cross-tenant behavior unchanged.
- API: `GET /workflows`'s `lastRun` field correct for success/failure/no-runs-yet cases; existing
  cross-tenant 404/401 behavior unaffected on all touched routes.
- Web: run-history panel inside `/workflows/[id]`, snapshot-diff polling with a bounded timeout, and
  a last-run indicator on `/`.
- `packages/domain`, `packages/engine`, and `packages/infrastructure` show zero diff. No Prisma
  migration or schema file touched. `POST /webhooks/:workflowId`'s response confirmed unchanged.
- Full quality gate (lint/typecheck/test/build) green, plus a backend-dependent E2E spec
  (`apps/web/e2e/run-history.spec.ts`) exercising execute → RUNNING → polling → terminal status →
  run detail, against a real running API + Postgres + Redis, and confirmation that
  `home.spec.ts`/`workflow-management.spec.ts` still pass.
