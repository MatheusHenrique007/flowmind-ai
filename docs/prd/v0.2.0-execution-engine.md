# PRD — Release v0.2.0: Minimal End-to-End Execution Engine

- **Status**: Draft — pending approval before implementation starts
- **Date**: 2026-08-07

## What problem does this release solve?

FlowMind AI has a solid foundation (v0.1.0) but zero proof that its core idea works: a trigger
firing, an AI step processing content, and an integration acting on the result — running
end to end, for real, with nothing mocked. Until that loop exists once, every architectural
decision made so far (the `AIProvider` port, Clean Architecture layering, the queue/persistence
stack) is unvalidated theory.

This release exists to answer one question: **does FlowMind's core mechanic actually work?**
Not "does it scale," not "can a user configure it visually" — just: fire a trigger, an AI step
runs, an action happens, and a human can see it happened. Everything else is deferred.

## Scope: exactly one use case

**Webhook trigger → Claude (summarize or classify) → Slack notification.**

Not a general-purpose engine. Not a framework for arbitrary workflows. One hardcoded pipeline,
built the right way (respecting the layering and the `AIProvider` port so it generalizes later),
but only one path actually wired up and working. Additional triggers/providers/destinations
(Email, GitHub, Notion, OpenAI, Gemini) come in later releases, one at a time, only after this
one is proven — see [ROADMAP.md](../../ROADMAP.md).

## User flow for this release

This release is proven via API calls and logs/dashboard reads — **not** through a visual editor
or a workflow-creation wizard. That UI-driven flow (create account → create workflow → pick
trigger → pick AI → pick destination → execute → view history) is real and is FlowMind's actual
product vision, but it belongs to a later release once the engine underneath it is proven. Build
that UI on top of an unproven engine and the risk is a good-looking editor wired to a core that
doesn't actually work.

The five product questions, answered for what v0.2.0 actually ships:

1. **Who uses this?** No end user yet. The "user" of this release is whoever is running the demo
   (us) — this release is a technical proof, demonstrated by triggering it directly.
2. **How do they create a workflow?** They don't, yet. The one workflow (webhook → Claude →
   Slack) is hardcoded — seeded in the database or defined in code, not authored through UI.
3. **How does it execute?** A `POST` to a webhook endpoint on the API creates a `WorkflowRun`,
   enqueues a job, a worker picks it up, calls Claude via `ai-factory`, then posts the result to
   a configured Slack channel via its webhook URL.
4. **How do they see the result?** Two ways: the Slack message itself (the demo's payoff), and a
   `GET` endpoint (or a plain page in `apps/web`) listing `WorkflowRun` history with status and
   timestamps — "did it run, when, did it succeed."
5. **How do they fix an error?** Out of scope for retries/edit flows this release. A failed run
   is recorded with its error and is visible in the run history — visibility, not recovery, is
   the bar for v0.2.0.

## Entities

Minimal persistence — just enough to record that a run happened and inspect it after the fact:

- **Workflow** — the (for now, single, hardcoded) definition: which trigger, which AI step
  config (provider, prompt/instruction), which destination.
- **WorkflowRun** — one execution instance of a Workflow: status (`pending` / `running` /
  `succeeded` / `failed`), timestamps, and a reference to its Workflow.
- **WorkflowStep** (or `RunStep`) — one step's outcome within a run (e.g. "AI step": input
  payload, output, latency, error if any). Keeping steps as their own record (not just a blob on
  `WorkflowRun`) is what lets the run history show _where_ a failed run failed, not just that it
  failed.

No `User`, `Organization`, or `Team` entities yet — no auth in this release (see Out of Scope).

## APIs needed

- `POST /webhooks/:workflowId` (or a fixed path for the one seeded workflow) — receives the
  inbound payload, creates a `WorkflowRun`, enqueues the execution job. Responds fast (202-style
  "accepted"), since the actual work happens asynchronously via BullMQ.
- `GET /workflow-runs` — lists runs (id, status, timestamps) for the run-history view.
- `GET /workflow-runs/:id` — a single run's detail, including its steps, for debugging/demo
  purposes.

No auth on these endpoints yet — see Out of Scope. OpenAPI/Swagger documentation for these three
endpoints is in scope (it's already wired as part of the frozen stack, just unused until now).

## Explicitly out of scope for this release

- Visual workflow editor / React Flow canvas — no UI-driven workflow creation.
- Authentication, multi-tenancy, `User`/`Organization` entities, JWT — the webhook endpoint is
  open for this release; this is a known, accepted, and documented gap for a local/demo-only
  release, not something silently skipped.
- Any trigger other than webhook (Email, GitHub, Notion, schedule/cron).
- Any AI provider other than Claude (OpenAI and Gemini adapters stay stubs).
- Any destination other than Slack.
- Retry logic, manual re-run, or workflow editing after creation.
- Billing, settings, teams, RBAC, marketplace — per the MVP rule in CONTRIBUTING.md.

## How this release is demoed in under two minutes

1. Send a webhook request (via `curl` or Postman) with some text content (e.g. a fake support
   ticket or email body) to the running API.
2. Show the terminal/log confirming a `WorkflowRun` was created and queued.
3. Show the Slack channel receiving the AI-generated summary/classification within seconds.
4. Open the run-history endpoint (or page) and show the completed run with its recorded steps.

That's the whole demo. If any of those four beats doesn't work reliably, the release isn't done.
