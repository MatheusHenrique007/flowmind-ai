# PRD — Release v0.2.0: Minimal End-to-End Execution Engine

- **Status**: Approved — frozen, implementation may start
- **Date**: 2026-08-07 (revised same day: Engine/contracts architecture added per review)

## What problem does this release solve?

FlowMind AI has a solid foundation (v0.1.0) but zero proof that its core idea works: a trigger
firing, an AI step processing content, and an integration acting on the result — running
end to end, for real, with nothing mocked. Until that loop exists once, every architectural
decision made so far (the `AIProvider` port, Clean Architecture layering, the queue/persistence
stack) is unvalidated theory.

This release exists to answer one question: **does FlowMind's core mechanic actually work?**
Not "does it scale," not "can a user configure it visually" — just: fire a trigger, an AI step
runs, an action happens, and a human can see it happened. Everything else is deferred.

## Scope: exactly one use case

**Webhook trigger → Claude (summarize or classify) → Slack notification.**

Not a general-purpose engine. Not a framework for arbitrary workflows. One hardcoded pipeline,
built the right way (respecting the layering and the `AIProvider` port so it generalizes later),
but only one path actually wired up and working. Additional triggers/providers/destinations
(Email, GitHub, Notion, OpenAI, Gemini) come in later releases, one at a time, only after this
one is proven — see [ROADMAP.md](../../ROADMAP.md).

## Engine architecture: the Engine never knows Claude or Slack

Even though exactly one AI provider and one destination are wired up this release, the Engine
that runs a workflow must not import or reference `ClaudeProvider` or `SlackDestination`
directly. It only knows two contracts:

- **`AIProvider`** — already exists (`packages/ai/contracts`, ADR-0001 Decision 3).
- **`Destination`** — new this release. Mirrors the `AIProvider` shape:
  `send(payload: DestinationPayload): Promise<DestinationResult>`. Lives in a new
  `packages/destinations/contracts` package, with `packages/destinations/slack` as the one real
  adapter (Discord/Email/Notion/GitHub destinations are future adapters, added the same way
  `ai/openai` and `ai/gemini` will be — see ADR-0001 Decision 3's pattern).

**The Engine rule**: a step's output never calls the next step directly. `ClaudeNode → SlackNode`
is never allowed as a direct call — the only path is `ClaudeNode → ExecutionContext → SlackNode`.
Every step reads from and writes to a shared `ExecutionContext`, not to the next step.

`ExecutionContext` is a plain object threaded through the run, not a persisted entity:

```json
{
  "input": "raw webhook payload",
  "variables": {},
  "steps": {
    "aiStep": { "output": "...", "startedAt": "...", "finishedAt": "..." }
  }
}
```

Each step reads what it needs from `ExecutionContext` and writes its result back into it; the
Engine passes the updated context to the next step. This is what lets a fourth, fifth, sixth step
type get added later without any earlier step's code changing.

**Provider and destination selection is a factory concern, not the Worker's.** The Worker's only
job is "execute this Engine run" — it never mentions Claude or Slack. `ai-factory` already
resolves `AIProvider` by name (ADR-0001); this release adds a matching `DestinationFactory` in
`packages/destinations/factory` that resolves `Destination` by name the same way. Adding
`DiscordDestination` or `EmailDestination` later touches the factory and a new adapter package —
never the Engine or the Worker.

```
Client
  │  POST /webhooks/:workflowId
  ▼
API (Fastify)
  │  enqueues job
  ▼
BullMQ (Redis)
  │
  ▼
Worker
  │  "execute this Engine run" — no knowledge of Claude/Slack
  ▼
Workflow Engine
  │
  ├─▶ AIProvider (via ai-factory)        ──▶ ClaudeProvider
  │     reads/writes ExecutionContext
  │
  └─▶ Destination (via DestinationFactory) ──▶ SlackDestination
        reads/writes ExecutionContext
  │
  ▼
Persistence (Prisma/Postgres): WorkflowRun + WorkflowStep records
```

## User flow for this release

This release is proven via API calls and logs/dashboard reads — **not** through a visual editor
or a workflow-creation wizard. That UI-driven flow (create account → create workflow → pick
trigger → pick AI → pick destination → execute → view history) is real and is FlowMind's actual
product vision, but it belongs to a later release once the engine underneath it is proven. Build
that UI on top of an unproven engine and the risk is a good-looking editor wired to a core that
doesn't actually work.

The five product questions, answered for what v0.2.0 actually ships:

1. **Who uses this?** No end user yet. The "user" of this release is whoever is running the demo
   (us) — this release is a technical proof, demonstrated by triggering it directly.
2. **How do they create a workflow?** They don't, yet. The one workflow (webhook → Claude →
   Slack) is hardcoded — seeded in the database or defined in code, not authored through UI.
3. **How does it execute?** A `POST` to a webhook endpoint on the API creates a `WorkflowRun`,
   enqueues a job, a worker picks it up, calls Claude via `ai-factory`, then posts the result to
   a configured Slack channel via its webhook URL.
4. **How do they see the result?** Two ways: the Slack message itself (the demo's payoff), and a
   `GET` endpoint (or a plain page in `apps/web`) listing `WorkflowRun` history with status and
   timestamps — "did it run, when, did it succeed."
5. **How do they fix an error?** Out of scope for retries/edit flows this release. A failed run
   is recorded with its error and is visible in the run history — visibility, not recovery, is
   the bar for v0.2.0.

## Entities

Minimal persistence — just enough to record that a run happened and inspect it after the fact:

- **Workflow** — the (for now, single, hardcoded) definition: which trigger, which AI step
  config (provider, prompt/instruction), which destination.
- **WorkflowRun** — one execution instance of a Workflow: status (`pending` / `running` /
  `succeeded` / `failed`), timestamps, and a reference to its Workflow.
- **WorkflowStep** (or `RunStep`) — one step's outcome within a run (e.g. "AI step": input
  payload, output, latency, error if any). Keeping steps as their own record (not just a blob on
  `WorkflowRun`) is what lets the run history show _where_ a failed run failed, not just that it
  failed.
- **ExecutionContext** — not a persisted entity, a plain in-memory object threaded through a run
  while it executes (see Engine architecture above). Each `WorkflowStep` record persists a
  snapshot of the context relevant to that step, once the run completes or fails.

No `User`, `Organization`, or `Team` entities yet — no auth in this release (see Out of Scope).

## Application layer: ExecuteWorkflow

The `ExecuteWorkflow` use case (`packages/application`) orchestrates a run, depending only on
three ports it defines and the Engine never implements directly: `WorkflowRepository`,
`WorkflowRunRepository`, `WorkflowEngine` (returning a typed `WorkflowExecutionResult`, never a
generic/untyped result), plus a `Clock` port defined for the Engine's future use (not yet
consumed here — see its own doc comment for why).

Sequence, and why the run is persisted three times rather than once:

```
findById(workflowId)              -- WorkflowNotFoundError if missing (application error,
                                      not HTTP; Presentation maps it to 404)
WorkflowRun.create()
save(run)                         -- PENDING, persisted immediately
run.start()
save(run)                         -- RUNNING
engine.execute(workflow, context)
run.complete() | run.fail()
save(run)                         -- terminal status
```

Persisting immediately after `create()` (before `start()`) means a crash between those two calls
still leaves a traceable `PENDING` run record, instead of the run's existence being lost
entirely. This is a deliberate trade-off, not an oversight: **three separate `save()` calls
without a transaction/Unit-of-Work wrapping them.** For this release's scope (one workflow, no
concurrent runs racing on the same aggregate) that's acceptable. Flagged here so it isn't
silently forgotten: **once multiple related persistence operations need to succeed or fail
together, evaluate introducing a Unit of Work or transactional boundary** — not implemented now,
because no current failure mode in this release's scope requires it (see the anti-overengineering
question below).

## The overengineering check

Applied throughout this release's design, and worth stating explicitly so it keeps being asked
in later releases: before adding any abstraction, ask **"does this solve a problem that exists
today, or one that might exist in six months?"** The `Clock` port above is a live example of
applying it — defined now because it's cheap and the shape is obvious, but not wired into
`ExecuteWorkflow` because nothing in this use case actually needs deterministic time yet.

## APIs needed

- `POST /webhooks/:workflowId` (or a fixed path for the one seeded workflow) — receives the
  inbound payload, creates a `WorkflowRun`, enqueues the execution job. Responds fast (202-style
  "accepted"), since the actual work happens asynchronously via BullMQ.
- `GET /workflow-runs` — lists runs (id, status, timestamps) for the run-history view.
- `GET /workflow-runs/:id` — a single run's detail, including its steps, for debugging/demo
  purposes.

No auth on these endpoints yet — see Out of Scope. OpenAPI/Swagger documentation for these three
endpoints is in scope (it's already wired as part of the frozen stack, just unused until now).

## Explicitly out of scope for this release

- Visual workflow editor / React Flow canvas — no UI-driven workflow creation.
- Authentication, multi-tenancy, `User`/`Organization` entities, JWT — the webhook endpoint is
  open for this release; this is a known, accepted, and documented gap for a local/demo-only
  release, not something silently skipped.
- Any trigger other than webhook (Email, GitHub, Notion, schedule/cron).
- Any AI provider other than Claude (OpenAI and Gemini adapters stay stubs).
- Any destination other than Slack.
- Retry logic, manual re-run, or workflow editing after creation.
- Billing, settings, teams, RBAC, marketplace — per the MVP rule in CONTRIBUTING.md.

## How this release is demoed in under two minutes

1. Send a webhook request (via `curl` or Postman) with some text content (e.g. a fake support
   ticket or email body) to the running API.
2. Show the terminal/log confirming a `WorkflowRun` was created and queued.
3. Show the Slack channel receiving the AI-generated summary/classification within seconds.
4. Open the run-history endpoint (or page) and show the completed run with its recorded steps.

That's the whole demo. If any of those four beats doesn't work reliably, the release isn't done.

## Approval

Approved. Four adjustments were required before freezing, from a Principal-Engineer-style
review, and are incorporated above:

1. The Engine never references `ClaudeProvider` or `SlackDestination` directly — only the
   `AIProvider` and `Destination` contracts.
2. A shared `ExecutionContext` is threaded through every step, instead of steps calling each
   other directly.
3. The Worker only executes the Engine; provider/destination selection is a factory concern
   (`ai-factory`, new `DestinationFactory`).
4. This document includes the API → Queue → Worker → Engine → Providers/Destinations →
   Persistence diagram above.

The standing rule for implementation: the Engine must never become an if/else on provider or
destination type. From v0.2.0 onward it executes a sequence of steps through contracts alone —
this is what lets OpenAI, Gemini, Notion, GitHub, and Discord get added later by adding adapters,
never by touching the Engine.

This PRD is now frozen — see the foundation-freeze and no-technical-debt-carryover rules in
[CONTRIBUTING.md](../../CONTRIBUTING.md) for how changes to it would be handled going forward.
