# PRD — Release v0.3.0: Visual Workflow Builder

- **Status**: Draft — pending approval before implementation starts
- **Date**: 2026-08-07

## What problem does this release solve?

Every workflow so far (`webhook-to-slack-demo`) is hardcoded — created by a seed script, never by
a user. FlowMind AI's actual product vision is a no-code visual editor; v0.2.x proved the
execution engine works, but proved nothing about _authoring_. This release exists to answer:
**can a user create a workflow through a UI, without touching code or the database, and have it
actually run through the same engine?**

## Scope: visual authoring of the same fixed shape — no new step types or providers

**A React Flow canvas that creates and saves a Trigger → AI → Destination workflow** — the exact
same shape v0.2.0 proved, just authored visually instead of seeded. Deliberately not expanding to
multiple providers, multiple destinations, or new step types in this release — that's a separate
axis of complexity (per the MVP rule in CONTRIBUTING.md) from "can we persist a workflow a user
just drew." Proving dynamic persistence and visual authoring together with provider/step
expansion would confound two risks in one release.

## The real risk this release proves

Every `Workflow` in the codebase today is hardcoded (seeded). There is no `POST /workflows`, no
use case for creating one, and no UI. The Domain already supports this — `Workflow.create()`
validates any composition satisfying its invariants (at least one Trigger/AI/Destination step,
Trigger first) — but Application and Infrastructure have no write path. **This release adds that
write path**, which means it necessarily touches Application (a new `CreateWorkflow` use case)
and Infrastructure (`PrismaWorkflowRepository` needs a `save`, not just `findById`) — the
"don't touch Application/Infrastructure" constraint from v0.2.1/v0.2.2 applied to _polish_
releases that followed a completed feature; this release's entire point is a new feature, so that
constraint doesn't apply here. Domain needs no changes — `Workflow.create()` already validates
correctly.

## User flow for this release

The five product questions:

1. **Who uses this?** The first real user this project has had: someone building a workflow
   through the UI, not running a script or querying an API directly.
2. **How do they create a workflow?** Drag three nodes onto a React Flow canvas — Trigger, AI,
   Destination — connect them in order, fill in each node's config (trigger kind; AI provider +
   instruction; destination + target), click Save.
3. **How does it execute?** A "Run" button (or the existing webhook endpoint, now pointed at a
   real, dynamically-created workflow ID) triggers the same queue → worker → Engine pipeline
   v0.2.0 already proved. No engine changes.
4. **How do they see the result?** The existing run-history API (`GET /workflow-runs`), now
   rendered in the UI instead of `curl`'d.
5. **How do they fix an error?** Edit the workflow's node config and re-run. No in-flight run
   editing, no versioning of past workflow definitions — out of scope.

## Entities and API surface

- **New**: `POST /workflows` (create), `PUT /workflows/:id` (edit) — both validated through
  `Workflow.create()`'s existing invariants, so an invalid composition (e.g. no Trigger first) is
  rejected the same way it always has been, just from a real API instead of a seed script.
- **New Application use cases**: `CreateWorkflow`, `UpdateWorkflow` — thin orchestration, same
  shape as `ExecuteWorkflow`: validate via Domain, persist via the repository port.
- **Extended port**: `WorkflowRepository` gains `save(workflow: Workflow): Promise<void>`
  (currently read-only, `findById` only).
- **No Domain changes** — `Workflow`/`WorkflowStep` already model everything this needs.

## Explicitly out of scope for this release

- Multiple AI providers or destinations in the same workflow, or provider/destination selection
  at authoring time beyond what already exists (Claude, Slack) — no OpenAI/Gemini/Discord UI.
- New step/trigger types (Email, GitHub, Notion, schedule/cron) — still webhook-only.
- Workflow versioning, run-time editing, or undo/redo on the canvas.
- Authentication/multi-tenancy — the editor is still single-tenant, no login.
- Node marketplace, sharing, or templates.

## How this release is demoed in under two minutes

1. Open the editor, drag Trigger → AI → Destination onto the canvas, connect them, fill in config
   (Claude instruction, Slack channel).
2. Click Save — show the workflow now exists via `GET /workflows/:id` (or in the UI itself).
3. Trigger a run (button or webhook) — show it executing through the existing pipeline.
4. Show the run landing in history, same as v0.2.0's demo — but this time, the workflow that ran
   was drawn by hand, not seeded.
