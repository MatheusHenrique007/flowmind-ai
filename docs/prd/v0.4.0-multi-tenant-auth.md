# PRD — Release v0.4.0: Multi-Tenant Auth (Basic)

- **Status**: Draft — pending approval before implementation starts
- **Date**: 2026-08-08

## What problem does this release solve?

Every workflow today is globally visible — there is no user, no workspace, no ownership. Anyone
who knows a workflow's UUID can read, edit, or execute it. This release proves the minimal
multi-tenant shape: **a user can register, log in, own exactly one Workspace, and only ever see
that Workspace's workflows** — nothing more.

## Scope: prove one flow, nothing beyond it

```
Register → Login → Workspace → Dashboard → Protected Workflow → Logout
```

1 user → 1 Workspace (created together, atomically, at registration). No teams, no invites, no
multiple workspaces per user, no RBAC beyond "you own your Workspace or you don't," no OAuth, no
billing. Anything not required for the flow above is out of scope — see "Explicitly out of
scope" below.

## Real risks this release proves

1. **Every persisted Workflow today has no owner.** Adding `workspaceId` to `Workflow` is a
   Domain contract change (`Workflow.create()` gains a required field) and a `WorkflowRepository`
   port change (`findById` must scope by workspace) — justified because without it, isolation
   would live only in ad-hoc SQL, not as an enforceable Domain/Application rule.
2. **The project has never run a real Prisma migration.** `prisma db push` is used everywhere
   (CI, `scripts/demo.mjs`, `packages/infrastructure`'s `db:push` script) and cannot backfill
   existing rows safely. Adding a required `workspace_id` column to a table that already has rows
   (the seeded demo workflow, anything created while testing v0.3.0's editor) needs an actual
   migration with a backfill step, not a `db push`. **This is a process change beyond schema
   edits** — it touches CI, the demo script, and the infrastructure package's scripts. Flagged
   explicitly per the discovery rules; implementation should not proceed on this point without
   the stakeholder's explicit confirmation.
3. **CORS is currently `origin: true`** (reflects any origin) — fine with no credentials involved,
   but incompatible with a secure cookie-based refresh token. Must become an explicit allow-list
   (`WEB_ORIGIN` env var) with `credentials: true`.

## Entities

- **User** (Domain, new): `id`, `email` (validated value object), `passwordHash` (value object,
  see Security), `workspaceId`, `createdAt`.
- **Workspace** (Domain, new): `id`, `name`, `ownerUserId`, `createdAt`. Trivial this release.
- **RefreshToken** (Domain, new): `id`, `userId`, `tokenHash` (SHA-256 of the opaque token, never
  the raw value), `familyId` (for reuse-triggered chain revocation), `expiresAt`, `revokedAt`
  (nullable). Behavior: `isExpired(now)`, `isRevoked()`, `revoke()`.
- **PasswordHash** (Domain value object, new): `PasswordHash.hash(plain): Promise<PasswordHash>`,
  `.verify(plain): Promise<boolean>` — implemented with `node:crypto`'s `scrypt`, no new
  dependency. Lives in Domain, same precedent as `EntityId` already using `node:crypto`
  (`randomUUID`) — Node's standard library is not "infrastructure" in the sense the project's
  existing rule (no `@prisma/client`/`fastify`/`bullmq`/vendor SDKs in Domain) actually targets.
- **Workflow** (Domain, changed): gains a required `workspaceId` on `Workflow.create()`.

## Ports (Application)

New: `UserRepository` (`findByEmail`, `findById`, `save`), `WorkspaceRepository` (`findById`,
`save`), `RefreshTokenRepository` (`save`, `findByTokenHash`, `revokeFamily`), `TokenService`
(`signAccessToken(claims): string`, `verifyAccessToken(token): Claims | null`) — the one genuinely
Infrastructure-backed auth port, since JWT signing needs an external library (`jose`) and a
secret from config. No port for password hashing — that stays a Domain concern (see above).

Changed: `WorkflowRepository.findById(id: WorkflowId, workspaceId: WorkspaceId): Promise<Workflow
| null>` — returns `null`, not an error, when the workflow exists but belongs to a different
workspace, so a cross-tenant access attempt is indistinguishable from a 404 (no enumeration via
403 vs 404).

## Use cases (Application)

New: `RegisterUser`, `LoginUser`, `RefreshSession`, `LogoutUser`, `GetCurrentUser`.

Changed: `CreateWorkflow`, `UpdateWorkflow`, `ExecuteWorkflow`, `GetWorkflowRun`,
`ListWorkflowRuns` all gain a `workspaceId` parameter, threaded through to the repository calls.

## API surface

- `POST /auth/register` — email + password. Creates User + Workspace atomically. Returns access
  token in the body; sets the refresh token as an httpOnly cookie.
- `POST /auth/login` — same response shape as register. Generic "invalid credentials" error for
  both wrong password and unknown email (no user enumeration via this endpoint).
- `POST /auth/refresh` — reads the refresh token cookie, rotates it, returns a new access token.
  Detects reuse of an already-rotated token (signal of theft) and revokes the entire token family.
- `POST /auth/logout` — revokes the current refresh token (or its whole family), clears the
  cookie.
- `GET /auth/me` — returns the authenticated user's id/email/workspaceId. 401 if not authenticated.
- All existing workflow/webhook/workflow-run routes gain an authentication `preHandler` that
  extracts `{ userId, workspaceId }` from the access token and passes `workspaceId` into the use
  case call. Missing/invalid/expired token → 401. Cross-tenant workflow id → 404 (via the changed
  repository contract above, not a distinct 403 code path).

## Authentication strategy

- **Passwords**: `crypto.scrypt` (Node built-in) — no bcrypt/argon2 assumed or added; nothing like
  it exists in the project today, and scrypt is OWASP-accepted, has no native-binding install
  risk (this exact machine already hit native-module friction with Docker/WSL2 earlier this
  project), and needs zero new dependency.
- **Access token**: short-lived JWT (15 min), signed via `jose` (ESM-native, fits this all-ESM
  monorepo better than `jsonwebtoken`'s CJS/callback API). Returned in the response body; the
  frontend keeps it in memory only — never `localStorage` (reduces XSS blast radius).
- **Refresh token**: opaque random value (`crypto.randomBytes(32)`), not a JWT. Stored as an
  httpOnly, Secure, `SameSite=Lax` cookie. The database stores only its SHA-256 hash — fast
  hashing is correct here (unlike passwords) because the token itself is already high-entropy;
  scrypt would cost CPU for no security gain against a 256-bit random value.
- **Rotation + reuse detection**: every `/auth/refresh` call revokes the presented token and
  issues a new one sharing the same `familyId`. If a already-revoked token is presented again
  (replay/theft signal), the entire family is revoked, logging out that whole session chain.
- **Cookies vs header, and CSRF**: refresh token in an httpOnly cookie (JS can't read it, limiting
  XSS token theft); access token in the `Authorization` header for every mutating request. Since
  the only cookie-authenticated endpoint is `/auth/refresh`, and `SameSite=Lax` already blocks
  that cookie being sent on a cross-site POST from another origin, a dedicated CSRF token is not
  added this release — documented as an accepted trade-off, not an oversight.
- **CORS**: `origin: true` (reflect-any) must become an explicit `WEB_ORIGIN`-driven allow-list
  with `credentials: true`, or the refresh cookie cannot be used securely.

## Multi-tenancy strategy

1 User : 1 Workspace, created together in one transaction during `RegisterUser`. `workspaceId` is
embedded as a JWT claim, extracted per-request by the auth `preHandler`, and passed explicitly
into every use case — Infrastructure never infers it implicitly from anywhere else.

## Database changes

New tables: `users`, `workspaces`, `refresh_tokens`. New column: `workflows.workspace_id`
(required), denormalized `workflow_runs.workspace_id` (defense in depth, avoids relying on a join
being correct for isolation).

**Migration approach, given existing data must survive**: this is the first schema change in the
project's history that must run against a database with real rows in it (the seeded demo
workflow, anything created testing v0.3.0). The plan: (1) create a default/system Workspace,
(2) add `workspace_id` as nullable, (3) backfill every existing `Workflow` row to that Workspace,
(4) alter the column to `NOT NULL`. This requires switching from `prisma db push` to
`prisma migrate` for this and future schema changes — see the ADR for the full reasoning. No
existing row is deleted or silently dropped.

## Explicitly out of scope for this release

Full RBAC, invites, teams/organizations, multiple workspaces per user, billing, OAuth/Google/
GitHub login, rate limiting on auth endpoints (a real, documented gap — brute-force protection is
deferred, not solved, tracked as follow-up debt), a dedicated CSRF token (see rationale above),
email verification, password reset.

## How this release is demoed in under two minutes

1. Register a new account — land on an empty Dashboard.
2. Create a workflow in the existing React Flow editor, save it.
3. Log out, log back in — the workflow is still there (same Workspace).
4. Open a second browser/incognito session, register a second account — its Dashboard shows no
   workflows; attempting to fetch the first account's workflow by ID returns 404, not the data.
5. Execute the workflow, show the run in history, log out.

## Test plan

Unit (Domain/Application, hand-written fakes, matching the project's existing pattern): valid/
invalid registration, duplicate email, weak password, valid/invalid login, access token issuance/
verification, refresh rotation, reuse detection revoking a family, logout revocation,
`WorkflowRepository.findById` scoping by workspace.

Integration (real Postgres, `describe.skipIf(!process.env.DATABASE_URL)` pattern already used):
`PrismaUserRepository`, `PrismaRefreshTokenRepository`, and a real cross-tenant isolation test
against the database.

Manual: the five-step demo flow above, plus explicitly attempting to call a protected route with
no token (expect 401) and with another workspace's workflow id (expect 404).
