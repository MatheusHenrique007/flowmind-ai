# PRD — Release v0.7.0: Workflow Management

- **Status**: Approved (stakeholder-approved in chat; this document formalizes it)
- **Date**: 2026-08-12

## What problem does this release solve?

The product could create and update exactly one Workflow at a time, but could never list or
reopen one. `WorkflowRepository` (Application port) only exposed `findById`/`save` — no listing
method. `apps/api/src/routes/workflows.ts` only registered `POST`/`PUT /workflows` — no `GET`. The
frontend (`apps/web/components/flow-editor.tsx`) tracked at most one Workflow in local component
state that reset on every page reload, with zero fetch-on-mount. A user creating Workflow A then
Workflow B silently orphaned A — no way to see or reopen it, even though its Postgres row still
existed.

## Who is this for, and what is the use case?

Any workspace owner who has created more than one Workflow (or reloaded the page after creating
one) and needs to find, reopen, and edit an existing Workflow instead of only ever being able to
build a new one from scratch.

## Scope: read paths plus frontend navigation, nothing else

```
WorkflowRepository.listByWorkspace (Application port)
   -> ListWorkflows / GetWorkflow (Application use cases)
   -> PrismaWorkflowRepository.listByWorkspace (Infrastructure)
   -> GET /workflows, GET /workflows/:id (API)
   -> "My Workflows" list page, editor reopen/edit flow (Web)
```

- `GET /workflows` — workspace-scoped list, lightweight shape (`{id, name}`, no steps).
- `GET /workflows/:id` — full detail (including reconstructed steps), 404 (never 403) for both a
  nonexistent id and another workspace's id — identical pattern to the existing
  `findById(id, workspaceId)` and `PUT /workflows/:id`.
- `ListWorkflows`/`GetWorkflow` Application use cases, mirroring `ListSchedules`'s and
  `UpdateWorkflow`'s existing style exactly. `GetWorkflow` throws the _existing_
  `WorkflowNotFoundError` — no new error type.
- `WorkflowRepository.listByWorkspace(workspaceId)` — a new query method against the existing
  `workflow` table, not a new column or table. `PrismaWorkflowRepository` mirrors
  `PrismaScheduleRepository.listByWorkspace` exactly.
- Frontend routing: `/` becomes the "My Workflows" list page (replacing the editor, which moves to
  `/workflows/new` for creating and `/workflows/[id]` for opening/editing). A new inverse mapper
  (`mapWorkflowToFlow`) reconstructs the fixed 3-node Trigger/AI/Destination shape into React Flow
  nodes/edges with a deterministic vertical layout — node positions were never persisted, so none
  are restored.

Anything not listed above is out of scope — see "Explicitly out of scope" below.

## Explicitly out of scope

- **Deleting a Workflow.** No `DELETE /workflows/:id`, no delete button anywhere in the frontend.
  A future release can add this without touching anything built here.
- **Any change to `packages/domain` or `packages/engine`.** `Workflow`/`WorkflowStep` already
  support everything this release needs.
- **Any change to the execution contract.** `POST /webhooks/:workflowId`, `ExecuteWorkflow`, and
  the `WorkflowInput`/`WorkflowDto` shapes are unchanged — this release is purely additive read
  paths plus navigation, not a change to how Workflows are created, updated, or executed.
- **A Prisma migration or schema change.** `listByWorkspace` is a new query against the existing
  `workflow` table's existing `workspaceId` column — no new column, no new table.
- **Restoring a Workflow's node positions.** They were never persisted
  (`PrismaWorkflowRepository.toStoredStep` only ever stored `{id, type, config}`), so reopening a
  Workflow always lays it out the same deterministic way a brand-new Workflow does.
- **Pagination, search, sorting, or filtering on the list page.** `GET /workflows` returns the
  workspace's full (small, MVP-scale) list; the frontend renders it as-is.

## Entities

No new Domain entities or value objects. `Workflow`/`WorkflowStep` (`packages/domain`) are
unchanged — this release only adds a new read path over data they already fully describe.

## APIs

- `GET /workflows` — `requireAuth`. 200 with the caller's workspace's Workflows, each shaped
  `{id, name}` (no steps — this is a lightweight listing, matching what `POST`/`PUT /workflows`
  already return). Empty array for a workspace with none.
- `GET /workflows/:id` — `requireAuth`. 200 with the full Workflow (`{id, name, steps}`) on
  success. 404 — never 403 — for both a nonexistent id and an id belonging to another workspace,
  matching `PUT /workflows/:id`'s existing behavior and ADR-0004.
- Both require the existing `requireAuth` bearer-token preHandler; workspace is always derived
  from the verified access token, never from the request.

## Execution flow

1. `GET /workflows` calls `ListWorkflows.execute(workspaceId)`, a thin passthrough to
   `WorkflowRepository.listByWorkspace(workspaceId)`, mapped to the lightweight `{id, name}` shape.
2. `GET /workflows/:id` calls `GetWorkflow.execute(workspaceId, workflowId)`, which reuses the
   existing workspace-scoped `findById` and throws `WorkflowNotFoundError` (→ 404) if the result is
   null — a workflow belonging to another workspace is indistinguishable from a nonexistent one.
3. On the frontend, `/` fetches `listWorkflows()` on mount and links each row to
   `/workflows/[id]`, plus a "New Workflow" link to `/workflows/new`.
4. `/workflows/[id]` fetches `getWorkflow(id)`, runs the result through `mapWorkflowToFlow` (fixed
   3-node deterministic layout, no restored positions), and initializes the editor's
   nodes/edges/name/saveState from it — the editor otherwise behaves exactly as it did before this
   release, including calling `updateWorkflow` on save instead of `createWorkflow`.
5. `/workflows/new` renders the editor with no `workflowId` — today's default hardcoded-new-workflow
   behavior, byte-for-byte unchanged.

## Real risks this release proves

1. **A Workflow saved before this release (with no persisted node positions) can be losslessly
   reopened into a valid, editable graph.** Proved by the inverse mapper's unit tests and by the
   full E2E flow: create → save → reopen → the same Trigger/AI/Destination data appears, re-laid
   out deterministically, and re-saving it round-trips correctly.
2. **Cross-tenant isolation holds for the new read paths exactly as it already does for the
   existing write paths.** Proved by Application-layer fake-based tests, Infrastructure-layer
   real-Postgres tests, and API-layer route tests, all following the same 404-not-403 pattern
   already established by `UpdateWorkflow`/`PUT /workflows/:id`.

## Two-minute demo

1. Log in (or register), landing on the new "My Workflows" list — empty for a fresh account.
2. Click "New Workflow", build and save a Workflow — the list now shows it, and the browser is
   back on `/`.
3. Create a second Workflow the same way — the list now shows both.
4. Click the first Workflow's name — the editor reopens with its Trigger/AI/Destination nodes and
   saved instruction/target text reconstructed, laid out top-to-bottom.
5. Edit the AI instruction and save — back on the list. Reopen the same Workflow — the edit
   persisted.

## Acceptance criteria / Definition of Done

- Application: `WorkflowRepository.listByWorkspace`, `ListWorkflows`, `GetWorkflow`, with
  fake-based tests covering listing (own workspace only, empty case) and getting (found,
  nonexistent, cross-tenant).
- Infrastructure: `PrismaWorkflowRepository.listByWorkspace`, with real-Postgres integration tests
  covering cross-tenant isolation and an empty workspace.
- API: `GET /workflows`, `GET /workflows/:id`, wired through `composition-root.ts`, with
  route-level tests covering happy paths, cross-tenant 404s, and unauthenticated 401s.
- Web: "My Workflows" list page at `/`, `/workflows/new`, `/workflows/[id]`, an inverse mapper with
  a deterministic layout, and an editor that fetches and reconstructs an existing Workflow on
  mount when given a `workflowId`.
- `packages/domain` and `packages/engine` show zero diff. No Prisma migration or schema file
  touched.
- Full quality gate (lint/typecheck/test/build) green, plus a backend-dependent E2E spec
  (`apps/web/e2e/workflow-management.spec.ts`) exercising the full
  register → create A → create B → list both → reopen A → edit → save → reload → persisted flow
  against a real running API + Postgres + Redis, and confirmation that the existing `home.spec.ts`
  (which runs with no backend) still passes against the new `/` page.
